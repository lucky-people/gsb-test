# cronspec —— 纯标准库 Cron 表达式解析与触发时间计算引擎

`cronspec` 是一个只依赖 Python 标准库的 cron 引擎，提供：

- 标准 5 字段 cron 表达式与 `@yearly` 等短写的严格解析；
- `matches` / `next_after` / `next_n` 触发时间计算（按字段推进，不做逐分钟扫描）；
- POSIX/Vixie 风格的「日（DOM）」与「星期（DOW）」并集语义；
- 稳定、确定的中文人类可读描述 `describe`。

不调用系统 `crontab` / `at` / `schtasks` 等任何外部命令，也没有任何第三方依赖。

## 快速开始

```python
from datetime import datetime
from cronspec import parse, describe

describe("* * * * *")          # 每分钟
describe("0 2 * * *")          # 每天 02:00
describe("30 9 * * MON,THU")   # 每周一、周四 09:30
describe("0 0 1 * *")          # 每月1日 00:00
describe("@hourly")            # 每小时整点

s = parse("0 0 13 * FRI")
s.matches(datetime(2024, 9, 13))          # True（既是 13 号又是周五）
s.next_after(datetime(2024, 9, 1))        # 2024-09-06 00:00
s.next_n(datetime(2024, 9, 1), 3)        # [9月6日, 9月13日, 9月20日]
```

对外接口仅暴露 `parse`、`describe` 与 `Schedule`：

```python
from cronspec import parse, describe, Schedule
```

## 字段语法

标准 5 字段：`分 时 日 月 周`，字段之间允许一个或多个空格或制表符，
首尾空白忽略（其余空白字符，如换行，不被当作分隔符）。

| 字段 | 允许范围 | 名字（大小写不敏感） |
| --- | --- | --- |
| 分 minute | `0-59` | 无 |
| 时 hour | `0-23` | 无 |
| 日 dom（day-of-month） | `1-31`（**不接受 0**） | 无 |
| 月 month | `1-12` | `JAN` … `DEC` |
| 周 dow（day-of-week） | `0-7`（`0` 与 `7` 都表示周日） | `SUN` … `SAT` |

字段内支持的写法：

- `*`：该字段全部合法值；
- 单值：`5`、`JAN`、`MON`；
- 范围：`1-5`、`MON-FRI`；范围起点不能大于终点（`5-1` 报错）；
- 步进：`*/15`、`0-30/10`、`MON-FRI/2`；步进必须是正整数，`*/0` 报错；
- 逗号组合：`1,15,30-40/5`，片段之间为「并集」并自动去重；
- 名字范围同样支持步进，如 `MON-FRI/2`。

短写（前后不允许再带字段）：

| 短写 | 等价表达式 |
| --- | --- |
| `@yearly` / `@annually` | `0 0 1 1 *` |
| `@monthly` | `0 0 1 * *` |
| `@weekly` | `0 0 * * 0` |
| `@daily` / `@midnight` | `0 0 * * *` |
| `@hourly` | `0 * * * *` |

## DOM/DOW 并集规则（重点）

当「日」与「星期」**两个字段都被显式限定**（都不是裸 `*`）时，
两者取**并集**：满足任意一个条件就触发，而不是「同时满足」。

- `0 0 13 * FRI`：每个 **13 号** 以及 **每个周五** 都会触发。
  例如 2024 年 9 月：6 日（周五）、13 日（周五，两个条件同时满足，只算一次）、
  20 日（周五）、27 日（周五），以及 10 月 13 日（周日，仅命中日号）。
- 只有「日」被限定时（如 `0 0 1 * *`）按日号判断，星期字段不参与；
- 只有「星期」被限定时（如 `0 0 * * 5`）按星期判断，日号不参与；
- 两者都是 `*` 时（如 `0 0 * * *`）每天都参与时/分判断。

关于 `*/n`：与 Vixie cron 一致，只要字段以 `*` 开头（包括 `*/15`），
在并集规则中仍视为「星号字段」；即 `0 0 */10 * 5` 中，DOW 被限定、
DOM 视为星号，仅按周五判断（`*/10` 枚举的 1/11/21/31 不参与 DOM 交集判断）。
`*/1` 的取值集合与 `*` 完全相同。

## Schedule API

- `parse(expr) -> Schedule`：解析表达式；任何非法输入都抛
  `cronspec.errors.ScheduleSyntaxError`。
- `Schedule.matches(dt) -> bool`：判断时刻是否命中。
  - 只接受**朴素 datetime**（`tzinfo` 为 None，或其 `utcoffset()` 为 None），
    带时区信息抛 `TypeError`；
  - **秒必须为 0**，否则一律返回 `False`（微秒不参与判断，建议调用前规整为 0）。
- `Schedule.next_after(dt) -> datetime`：返回**严格晚于** `dt` 的下一个触发时刻。
  即使 `dt` 本身就是触发时刻，返回的也是下一次；不修改入参。
- `Schedule.next_n(dt, n) -> list[datetime]`：接下来 n 个触发时刻，
  严格升序、不重复；`n <= 0` 抛 `ValueError`。
  可搜索年份范围为 `1..9999`（受 `datetime` 本身限制）；若表达式在此范围内
  永远没有触发时刻（如 `0 0 30 2 *`，2 月不可能有 30 号），抛
  `cronspec.errors.NoMatchingTimeError`。

### 错误对象字段

`ScheduleSyntaxError` 携带以下定位信息，全部基于**原始表达式**：

- `field`：字段名（`minute`/`hour`/`dom`/`month`/`dow`）；
  字段数不对或短写非法时为 `None`；
- `value`：出错片段原文（空片段时为空串 `""`；字段数错误时为整个表达式）；
- `position`：出错片段在原始表达式中的起始下标（0 基）；
- 异常信息本身为中文说明。

示例：

```python
from cronspec.errors import ScheduleSyntaxError

try:
    parse("0 60 * * *")
except ScheduleSyntaxError as e:
    e.field      # 'minute'
    e.value      # '60'
    e.position   # 2
```

解析器坚持「不静默纠正、不截断、不猜测意图」：`JANUARY`、`MONDAY`、
`@never`、范围/步进中混入非数字非名字字符等全部直接报错。

## 搜索算法与复杂度

核心搜索在 `cronspec/engine.py` 中，基于 `(年, 月, 日, 时, 分)` 整数元组，
从候选时刻开始按字段「跳到下一个合法值」，每轮迭代至少让一个字段向前跳动：

1. **月**：在允许月份的有序集合中二分查找 `>= 当前月` 的值；
   不存在则年 +1 并回到最小月，日/时/分归零。
2. **日**：在当月内直接计算最近的合法日，而不是逐天试：
   - 仅限定 DOM：集合中 `>= 当日` 的最小日号（要求不超过当月天数）；
   - 仅限定 DOW：由当日星期一次性算出集合中最近的星期偏移（0..6 天）；
   - DOM、DOW 都限定：分别算出候选后取较早者（并集语义）。
   当月找不到候选就跳到下一允许月份。
3. **时**：二分查找 `>= 当前小时` 的允许小时，找不到则日期进位重来；
   命中后分钟归零。
4. **分**：二分查找 `>= 当前分钟` 的允许分钟；找不到则小时进位重来。

每个字段集合都是解析期归约好的**升序去重元组**，跳转用二分查找
（`bisect`，O(log m)，m 为该字段取值个数，最多 60）。

- 单次 `next_after` 的外层迭代次数上界约为
  「月跳跃次数 + 日跳跃次数 + 时/分进位次数」，对正常表达式是常数级；
  即使是 `0 0 30 2 *` 这种不可达表达式，也只在年份越过边界（9999）时
  立刻终止并抛 `NoMatchingTimeError`，**不会死循环**。
- 稀疏表达式（每年一次、每 4 年一次）与每分钟表达式的单次推进成本同阶，
  绝不随时间跨度线性增长。

星期计算用格里高利历序号公式（`365y + y//4 - y//100 + y//400 + 年内日数`），
不依赖 `datetime.weekday()`，因此引擎内部的元组迭代器可以工作在
`datetime` 的年份上限（9999）之外，供基准测试使用；闰年判定为
「能被 4 整除且（不能被 100 整除或能被 400 整除）」。

## 边界与确定行为

- **闰年与 2 月 29 日**：`0 0 29 2 *` 只在 2 月有 29 天的年份触发，
  2000 年触发、1900/2100 年不触发；`0 0 30 2 *` 永远不可达，
  调 `next_after` 抛 `NoMatchingTimeError`。
- **31 号跳过短月**：`0 0 31 * *` 自动跳过没有 31 号的月份
  （2、4、6、9、11 月），序列为 1/31、3/31、5/31、7/31……
- **跨年推进**：`0 0 1 1 *` 在 12 月 31 日之后落到次年 1 月 1 日；
  月份进位在引擎内直接处理。
- **当天稍晚 vs 当天已过**：`0 9-17 * * *`，12:30 之后返回当天 13:00；
  18:00 之后返回次日 09:00。
- **分钟边界**：`0,59 * * * *` 在 10:00 之后给 10:59，10:59 之后给 11:00。
- **严格晚于**：`next_after` 先把输入截断到整分再 +1 分钟作为搜索起点，
  所以输入恰好是触发点时也会得到下一次；入参本身不被修改。
- **`*/1` 等价 `*`**：取值集合同为完整范围，星号语义也相同。
- **重复值去重**：`1,1,1` 等价 `1`，`1-3,2,3` 等价 `1-3`。
- **列表与范围/步进混合**：`1-5,20-25/2` → `1,2,3,4,5,20,22,24`。
- **步进大于跨度**：`*/90`（分字段）确定地得到仅 `0`；`55-57/10` 得到仅 `55`。
- **DOW 的 7**：单值 `7` 与范围右端 `7`（如 `0-7`）都归一为周日 0，
  `0-7` 展开为完整的 0..6。

## 人类可读描述

`describe(expr)` 返回确定的中文描述，同一表达式每次输出完全一致，
不依赖运行环境。部分示例：

| 表达式 | 描述 |
| --- | --- |
| `* * * * *` | 每分钟 |
| `0 2 * * *` | 每天 02:00 |
| `30 9 * * MON,THU` | 每周一、周四 09:30 |
| `0 0 1 * *` | 每月1日 00:00 |
| `0 0 13 * FRI` | 每月13日以及每周五 00:00 |
| `0 0 1 JAN-MAR *` | 1月、2月、3月的1日 00:00 |
| `@hourly` | 每小时整点 |
| `*/15 * * * *` | 每小时的 第 0 分、第 15 分、第 30 分、第 45 分 |

描述只用于人读，不保证可以反解析回表达式。

## 本机实测数据

测试环境：Windows，CPython 3.12.3（x64）。运行 `python bench.py`。
**耗时与峰值内存分开独立测量**：计时窗口内不启用 `tracemalloc`；
内存窗口内单独再跑一遍，报告 `tracemalloc.get_traced_memory()` 的峰值，
因此 tracemalloc 的追踪开销不会计入耗时。

连续取 **100,000** 个触发时刻：

| 表达式 | 耗时（秒） | 吞吐（个/秒） | 峰值内存 |
| --- | --- | --- | --- |
| `0 0 1 1 *`（每年 1 月 1 日，内部元组迭代器） | ≈ 0.40 | ≈ 25 万 | ≈ 336 B |
| `0 0 29 2 *`（闰年 2 月 29 日，内部元组迭代器） | ≈ 0.66 | ≈ 15 万 | ≈ 368 B |
| `* * * * *`（每分钟，内部元组迭代器） | ≈ 0.12 | ≈ 85 万 | ≈ 304 B |
| `* * * * *`（每分钟，公开 datetime API） | ≈ 0.39 | ≈ 26 万 | ≈ 4.58 MiB |

README 要求的性能门——从 `2020-01-01 00:00` 起，用公开 datetime API
连续取 **1000** 个触发时刻（耗时与内存同样分开测量）：

| 表达式 | 耗时 | 峰值内存 |
| --- | --- | --- |
| `0 0 1 1 *` | ≈ 9.1 ms | ≈ 47.9 KiB |
| `0 0 29 2 *` | ≈ 12.3 ms | ≈ 47.9 KiB |

两者均远低于 1 秒门限。

说明：两个稀疏表达式取 10 万个触发时刻会推进到公元数十万年
（闰年 2 月 29 日约需要 40 万年），超出 `datetime` 的年份上限（9999），
因此这两行使用引擎内部同一套算法的整数元组迭代器（`Schedule._iter_tuples`，
不做 datetime 包装、不保存结果列表）；高频表达式两种路径都给出了数据，
公开 API 的约 4.58 MiB 峰值主要是 10 万个 `datetime` 结果对象本身，
与搜索算法无关。

## 与系统 crontab 的行为差异

- 本库只做**表达式计算**（给定表达式与某个时刻，求匹配/下一次），
  不注册、不执行任何系统任务，也不调用 `crontab`、`at`、`schtasks` 等命令。
- 标准 vixie cron 支持秒级扩展（如 Quartz 的 6/7 字段）、`%` 特殊字符、
  `L/W/#` 等非标准修饰符（月末、最近工作日、第 N 个星期几）；
  本库**均不支持**，遇到即按语法错误处理。
- vixie cron 的短写（`@reboot` 除外）与本库一致；`@reboot` 语义依赖
  守护进程启动事件，本库不支持。
- 许多系统 cron 对字段数不足采用宽容补默认值的策略；本库严格要求恰好
  5 个字段（或单个合法短写），否则报错，不做任何猜测式纠正。
- 系统 cron 受 DST/时区影响（本地时间可能出现不存在或重复的墙钟时刻）；
  本库只接受**朴素 datetime**，按格里高利历规则纯数学推进，不涉及时区与夏令时。
- 系统 cron 通常以整分为最小粒度，秒字段概念不存在；本库同样以整分粒度
  匹配（`matches` 要求秒为 0），`next_after` 返回的时刻秒与微秒均为 0。
- 搜索范围受 Python `datetime` 可表示范围约束（年份 1..9999）；
  不可达表达式（如 2 月 30 日）在此范围内确定地抛 `NoMatchingTimeError`，
  而系统 cron 只会静默地永远不触发。

## 包结构

| 文件 | 职责 |
| --- | --- |
| `cronspec/__init__.py` | 对外入口，只暴露 `parse`、`describe`、`Schedule` |
