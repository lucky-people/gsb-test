# cronspec

纯 Python 标准库实现的 **Cron 表达式解析与触发时间计算引擎**。不依赖任何
第三方库，也不调用系统 `crontab` / `at` / `schtasks` 等命令。

```python
from datetime import datetime
from cronspec import parse, describe

schedule = parse("30 9 * * MON-FRI")
schedule.matches(datetime(2024, 9, 23, 9, 30))   # True
schedule.next_after(datetime(2024, 9, 23, 8, 0)) # datetime(2024, 9, 23, 9, 30)
schedule.next_n(datetime(2024, 9, 23, 9, 30), 3) # 接下来 3 个触发时刻
describe("30 9 * * MON,THU")                      # '每周一、周四 09:30'
```

## 字段语法

标准 5 字段写法：`分 时 日 月 周`，字段间允许一个或多个空格或制表符，
首尾空白会被忽略（字段内部不允许空白）。

| 位置 | 字段 | 取值范围 | 名字 |
| ---- | ---- | -------- | ---- |
| 1 | 分 | 0–59 | — |
| 2 | 时 | 0–23 | — |
| 3 | 日（DOM） | 1–31 | — |
| 4 | 月 | 1–12 | `JAN`…`DEC`（大小写不敏感） |
| 5 | 周（DOW） | 0–7，`0` 和 `7` 都表示周日 | `SUN`…`SAT`（大小写不敏感） |

每个字段都支持：

- `*`：该字段全部取值；
- 单值：`5`；
- 范围：`1-5`，范围必须从小到大，`5-1` 报错；
- 步进：`*/15`、`0-30/5`，步进必须是正整数，`*/0` 与 `*/-2` 报错；
- 逗号组合（上述写法可任意混合）：`1,15,30-40/5`；
- 名字可以参与范围：`MON-FRI`、`jan-mar/2`。

短写：

| 短写 | 等价表达式 |
| ---- | ---------- |
| `@yearly` / `@annually` | `0 0 1 1 *` |
| `@monthly` | `0 0 1 * *` |
| `@weekly` | `0 0 * * 0` |
| `@daily` / `@midnight` | `0 0 * * *` |
| `@hourly` | `0 * * * *` |

不支持 `@reboot`（它描述一次性启动事件，不属于周期计划）。

### 严格校验

任何非法输入都抛 `cronspec.errors.ScheduleSyntaxError`。异常对象带有：

- `field`：字段名（`minute` / `hour` / `day_of_month` / `month` /
  `day_of_week`）；字段数不对或短写非法时为 `None`；
- `value`：最小出错片段原文；
- `position`：`value` 在**原始表达式**中的起始下标（0 基）；
- `str(error)`：中文说明。

解析器不会静默纠正、截断或猜测意图，例如 `12/2`（裸值带步进，不是
`*/n` 或 `a-b/n`）会直接报错。

### 错误定位约定

`ScheduleSyntaxError` 的 `field` / `value` / `position` 遵循统一定位约定，
界面可以直接拿 `position` 与 `len(value)` 高亮出错文本：

- `field`：出错字段名；字段数不对或短写非法时为 `None`；
- `value`：**最小出错片段原文**——只包含出错的那一段（越界的数字、非法的
  步进值、写错的名字等），而不是整个字段；「缺失」类错误（空片段、未闭合
  范围）为空字符串，指向应当有内容的位置；
- `position`：`value` 在**原始表达式**中的 0 基起点。

**不变量**：对字符串表达式 `expr` 恒有
`expr[position:position + len(value)] == value`。

常见错误类别与 `value` 的取值对照：

| 错误类别 | 示例 | `field` | `value` | 说明 |
| -------- | ---- | ------- | ------- | ---- |
| 数字越界 | `60 0 * * *` | `minute` | `'60'` | 越界的那个数字 |
| 范围倒序 | `5-1 0 * * *` | `minute` | `'5-1'` | 整个倒序范围 |
| 步进非法 | `*/0 0 * * *` | `minute` | `'0'` | 非法步进值本身 |
| 空片段 | `1,,2 0 * * *` | `minute` | `''` | 空串，指向两个逗号之间 |
| 未知名字 | `0 0 * JANUARY *` | `month` | `'JANUARY'` | 未被支持的名字 |
| 非法范围字符 | `0 a * * *` | `hour` | `'a'` | 非法的记号本身 |
| 字段数错 | `0 0 1 *` | `None` | `'0 0 1 *'` | 去除首尾空白后的整个表达式 |
| 短写非法 | `@never` | `None` | `'@never'` | 非法短写词 |
| 未闭合范围 | `0 0 * jan- *` | `month` | `''` | 空串，指向缺少结束值的位置 |
| 字符嵌套在名字位置 | `0 0 * * FRI/SAT` | `day_of_week` | `'SAT'` | 出现在步进位置的名字 |

## DOM/DOW 并集规则（重点）

本引擎遵循 **POSIX / vixie cron** 的日匹配语义：

> 当「日（DOM）」与「周（DOW）」两个字段**都被显式限定**（词法上都不是
> `*`）时，两者取**并集**——满足任意一个即触发；只有一个被限定时按限定
> 的那个判断；两个都是 `*` 时每天参与判断。

```
0 0 13 * FRI
```

含义是“**每个 13 号**”**以及**“**每个周五**”都会在 00:00 触发，而不是
“13 号且周五”。例如 2024-09-13（周五）、2024-09-20（周五）和任意月份的
13 号都会命中，2024-09-14（周六且非 13 号）不命中。

与“并集触发”配套的词法约定：只要字段里出现星号（包括 `*/n`），该字段就
被视为“未限定”。因此 `*/2 * * * MON` 与 `* * * * MON` 一样，只在周一
触发（这与 vixie cron 对 `DOM_STAR`/`DOW_STAR` 的处理一致）。

## 触发时间计算

`Schedule` 上有三个方法，只接受**朴素** `datetime`（`tzinfo` 必须为
`None`，否则抛 `TypeError`）：

- `matches(dt) -> bool`：判断某时刻是否命中；秒或微秒不为 0 一律返回
  `False`。
- `next_after(dt) -> datetime`：返回**严格晚于** `dt` 的下一个触发时刻；
  不会修改入参。整分时刻不晚于同分钟内的任何输入（例如输入 12:00:59 时
  12:00 不算“之后”），因此始终从下一分钟开始找。
- `next_n(dt, n) -> list[datetime]`：返回接下来 `n` 个触发时刻，严格升序、
  不重复；`n <= 0` 抛 `ValueError`。

### 不可能存在的计划

若表达式在可搜索范围内没有任何触发时刻（例如 `0 0 30 2 *`，2 月永远没有
30 号），调用 `next_after` / `next_n` 会立即抛
`cronspec.errors.NoMatchingTimeError`，不会死循环。

## 搜索算法与复杂度

核心搜索**按字段推进**，绝不逐分钟线性扫描（`cronspec/engine.py`）：

1. **月份**：用 `bisect` 在允许月份的有序集合中跳到 `>= 当前月` 的第一个；
   年内没有就跨年。
2. **日**：在当前月内
   - DOM 受限时，用 `bisect` 找下一个允许日；
   - DOW 受限时，用纯整数算术计算星期并跳到下一个允许星期（星期集合最多
     7 个值）；
   - 两者都受限时取两者的较小值（并集语义）；
   - 日期超出本月天数（如 31 号落在 30 天的月份）直接跳到下一个允许月。
3. **时、分**：同样用 `bisect` 在有序集合中跳到 `>= 当前时/分` 的第一个；
   小时耗尽则回退到下一个候选日，分钟耗尽则回退到下一个小时。

闰年、月份天数、星期换算全部使用 Howard Hinnant 的公历整数算法
（`_days_from_civil` 及逆变换），不构造 `datetime.date`，因此内部
`(年, 月, 日, 时, 分)` 五元组搜索不受 `datetime` 的 9999 年上限限制。

**复杂度**：设命中前需要考察的候选月数为 `Y`（通常为 0–1），每次 `next_after`
为 `O(Y · (log 12 + 7 · O(1) + log 24 + log 60))`；月内只考察命中的候选日，
不遍历每天。连续取 `n` 个触发时刻为 `n` 次上述跳跃的总和。搜索窗口上限为
400 年（公历星期与闰年的完整重复周期），可行表达式必然在该窗口内命中。

## 边界行为

- **闰年 / 2 月 29 日**：`0 0 29 2 *` 命中 2020、2024、2028……；2100 年
  不是闰年（能被 100 整除但不能被 400 整除），自动跳到 2104 年。
- **31 号**：`0 0 31 * *` 自动跳过 2/4/6/9/11 月。
- **跨年**：12 月 31 日后自动推进到次年 1 月。
- **当天稍晚 / 已过时刻**：入参时刻早于当天触发点则命中当天，否则顺延。
- **0 分 / 59 分边界**：`0,59 * * * *` 在 00:59 之后下一个是 01:00。
- **`*/1` 与 `*` 等价**，且都被视为“未限定”字段。
- **重复值去重**：`1,1,1` 等价于 `1`。
- **范围与列表混合**：`1-5,20-25/2` 展开为
  `1,2,3,4,5,20,22,24`。
- **微秒**：`matches` 在微秒非 0 时返回 `False`；`next_after` 把带微秒的
  入参视为该分钟已经开始。

## 与系统 crontab 的行为差异

- 只处理 5 字段标准计划与 7 个时间短写；没有用户、环境变量、命令执行、
  `@reboot`、夏令时等概念。
- 返回的是朴素 `datetime`，不涉及时区；带时区的入参会被拒绝而不是隐式
  转换。
- 不存在“系统错过任务后补跑”的启动行为；`next_after` 纯粹做日历推算。
- DOW 内部统一以 0=周日表示（7 归一化为 0）；对外 API 不暴露 7。
- 受 `datetime` 年份范围（1–9999）限制，`next_after` / `next_n` 的结果若
  超出该范围会抛 `NoMatchingTimeError`；`bench.py` 的超大规模稀疏场景直接
  使用内部五元组，因此不受此限制。

## 人类可读描述

`describe(expr)` 返回确定性的中文描述，同一表达式每次输出完全一致：

| 表达式 | 描述 |
| ------ | ---- |
| `* * * * *` | 每分钟 |
| `0 2 * * *` | 每天 02:00 |
| `30 9 * * MON,THU` | 每周一、周四 09:30 |
| `0 0 1 * *` | 每月 1 日 00:00 |
| `@hourly` | 每小时整点 |
| `0 0 13 * FRI` | 每月 13 日或周五 00:00 |

描述只便于人读，不保证能被反解析回表达式。

## 模块结构

```
cronspec/
├── __init__.py   # 对外只暴露 parse、describe、Schedule
├── errors.py     # ScheduleSyntaxError、NoMatchingTimeError
├── fields.py     # 字段取值集合、CronField、Schedule 与 DOM/DOW 匹配
├── parser.py     # 词法分析、字段解析、中文描述
└── engine.py     # 历法换算与按字段推进的触发时间搜索
```

## 性能基准

```
python bench.py
```

基准对每个场景分别运行两轮：一轮**只计时**（不开启 `tracemalloc`），
一轮**只测峰值内存**（`tracemalloc.start()` 包裹生成过程），因此
tracemalloc 的追踪开销不会计入耗时窗口。

### 本机实测数据

环境：Windows + CPython 3.12.3，每个场景连续取 **100,000** 个触发时刻。

| 场景 | 耗时 | 峰值内存 |
| ---- | ---- | -------- |
| 稀疏：`0 0 1 1 *`（每年 1 月 1 日，内部五元组） | 约 354 ms | 约 11.3 MiB |
| 稀疏：`0 0 29 2 *`（闰年 2 月 29 日，内部五元组） | 约 551 ms | 约 11.3 MiB |
| 高频：`* * * * *`（每分钟，返回 datetime） | 约 231 ms | 约 4.6 MiB |

其中需求给出的 `0 0 1 1 *` 与 `0 0 29 2 *` 从 `2020-01-01 00:00` 起
连续取 **1000** 个触发时刻，在本机仅为毫秒量级（约 4 ms），远低于 1 秒。

> 注：以上数字为开发机实测，硬件与负载不同会有波动；可随时重新运行
> `python bench.py` 获取当前机器数据。
